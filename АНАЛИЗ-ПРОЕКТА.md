# 📊 Анализ проекта «Python — Основы программирования»

> Дата анализа: 07.07.2026
> Объект: статический образовательный сайт `python-web` (50 уроков Python, PWA + PHP-песочница)

Документ содержит результаты технического аудита проекта, выявленные проблемы и приоритизированные рекомендации по улучшению.

---

## 1. Общая характеристика проекта

**Что это:** многостраничный статический образовательный сайт на русском языке с курсом из **50 уроков** по Python.

**Стек и возможности:**

- HTML5 + CSS3 (один файл `style.css`, ~1350 строк) + ванильный JavaScript (`script.js` ~1089 строк, `config.js` ~780 строк).
- **PWA** — `manifest.json`, service worker `sw.js` (офлайн-режим).
- **PHP-бэкенд** для запуска Python-кода: `sandbox/run.php` (stateless), `sandbox/repl.php` (stateful REPL), `router.php` (dev-сервер).
- Прогресс, квизы, значки/достижения — на `localStorage`.
- Подсветка синтаксиса — `highlight.js` с CDN.
- SEO: meta-теги, Open Graph, JSON-LD schema.org `Course`.
- Интеграция с внешней площадкой заданий (`contest.nayanovaacademy.ru`).

**Общая оценка:** проект функционально богатый и хорошо проработанный содержательно. Основные слабые места — **рассинхронизация навигации после перенумерации курса (34→50 уроков)**, **устаревшая документация**, **безопасность песочницы**, **отсутствие шаблонизации** (масштабируемость) и **устаревший стиль JS-кода**.

> ⚠️ **Ключевой вывод:** курс был расширен и перенумерован с ~34 до 50 уроков, но вспомогательные артефакты (кэш service worker, карта курса, шпаргалки, README, manifest) **не были обновлены**. Это первопричина большинства критических проблем ниже — сломанная навигация и офлайн-режим.

### 2.2. Безопасность песочницы

Песочница запускает **произвольный код пользователя** — это самый чувствительный компонент.

**Проблемы:**

1. **`repl.php` слабее защищён, чем `run.php`.**
   - `run.php` запускает Python с изоляцией: `python3 -I -S` (игнорирование окружения и site-пакетов).
   - `repl.php` запускает `python3 -X utf8` **без флагов `-I -S`** — окружение и пользовательские пакеты доступны. Изоляцию нужно выровнять.

2. **Десериализация pickle = удалённое выполнение кода.**
   - REPL сохраняет состояние namespace через `pickle` (`load`/`dump`). `pickle.load` небезопасен: подделка/повреждение файла состояния потенциально ведёт к RCE.
   - **Файл состояния завязан на клиентский `session_id`:** `repl.html` генерирует UUID в `localStorage` и передаёт его в `repl.php` (в теле запроса и в `sendBeacon` при `beforeunload`). Клиент управляет именем файла состояния → нужна строгая валидация/санитизация `session_id` на сервере (только `[a-f0-9-]`), иначе возможен path traversal и подмена pickle-файла.
   - Рекомендуется:
     - хранить состояние в изолированном каталоге с непредсказуемыми именами и строгими правами;
     - валидировать `session_id` как строгий UUID;
     - рассмотреть замену `pickle` на безопасный формат (JSON для простых типов) или полную изоляцию сессии в контейнере.


3. **Дублирование кода раннера.** `sandbox/.repl_runner.py` — почти копия инлайн-раннера внутри `repl.php`. Одну логику нужно поддерживать в одном месте (риск расхождения правил валидации).

4. **Ограничения ресурсов.** Убедиться, что для обоих скриптов заданы: таймаут выполнения, лимит памяти/CPU, запрет сети, ограничение размера вывода. (Rate limiting в `run.php` есть — проверить наличие эквивалента в `repl.php`.)

5. **`permissions.sh` выполняет «живой» `curl`-тест против `run.php`** — деплой-скрипт не должен инициировать выполнение кода; вынести проверку в отдельный health-check.

**Рекомендация:** привести `repl.php` к уровню изоляции `run.php`, устранить/обезопасить `pickle`, объединить раннеры, зафиксировать лимиты ресурсов, запускать под минимально привилегированным пользователем (в идеале — в контейнере/namespace-изоляции).

## 3. Важные проблемы (Medium priority)

### 3.1. Отсутствие шаблонизации — проблема масштабируемости

- В `index.html` **все 50 карточек уроков прописаны вручную** (статический HTML, 13 групп-разделов).
- Навигация («Назад»/«Далее», меню) **захардкожена в каждом файле урока**.
- `mindmap.html`, `cheatsheets.html`, `repl.html` содержат крупные инлайн-блоки `<style>` (по ~50–250 строк) и инлайн-`<script>` (в `repl.html` ~250 строк логики REPL прямо в странице) — дублирование и рассинхрон стилей/логики.

Любое изменение (добавление урока, переименование, правка меню) требует ручных правок в десятках файлов → высокий риск рассинхронизации. Именно это уже привело к битым ссылкам в `sw.js`, `mindmap.html` и неверным номерам в `cheatsheets.html` (см. п. 2.0).


**Рекомендация:** ввести единый источник данных о уроках (например, `lessons.json`) и генерировать:
- карточки на главной,
- навигацию и хлебные крошки,
- боковое меню/оглавление
— из этого источника (клиентский рендер или статический билд-скрипт).

### 3.2. Баги в `config.js` (система значков и квизов)

- **Значок `func_guru` («Мастер функций»)** проверяет уроки `[23,24,25]`, но урок 25 — «Списки», а функции это уроки 22/23/24. Условие получения значка привязано к неправильным урокам.
- **Значок `oop_master`** проверяет `[42,43]`, но урок 43 — «Декораторы», а ООП — уроки 41/42.
- Комментарий утверждает «ровно 10 вопросов», но некоторые квизы содержат **9** (например, урок 15).
- **`final-test.html`** заявляет «тест содержит **50 вопросов**» — нужно проверить, что итоговый квиз в `config.js`/`script.js` действительно содержит ровно 50 вопросов (учитывая уже найденные квизы с 9 вместо 10, число, вероятно, не совпадает).

**Рекомендация:** исправить индексы уроков в `BADGES`; добавить автотест/проверку, что каждый квиз содержит заявленное число вопросов (включая итоговый — 50).


### 3.3. Качество JS-кода

- Везде используется `var` → устаревший стиль, засорение глобального пространства имён.
- **10+ отдельных обработчиков `DOMContentLoaded`** — хрупко и неэффективно.
- `script.js` монолитен (~12 анонимных IIFE), нет модулей и сборки.
- Огромный объём данных квизов инлайн в `config.js`.

**Рекомендация:**
- перейти на `const`/`let`, ES-модули;
- объединить инициализацию в один `DOMContentLoaded`;
- вынести данные квизов в отдельный `quizzes.json`;
- при желании — добавить лёгкий бандлер (esbuild/Vite) для минификации.

### 3.4. SEO и офлайн-подсветка

- В `index.html` **нет** `canonical`, `og:image`, `og:url`, Twitter Cards.
- Нет `sitemap.xml` и `robots.txt`.
- `highlight.js` подключается с CDN **без SRI (integrity)** и без офлайн-фолбэка — это противоречит цели PWA (офлайн-режим): без сети подсветка кода сломается.

**Рекомендация:** добавить недостающие meta/OG-теги и `og:image`; сгенерировать `sitemap.xml` + `robots.txt`; добавить SRI-хеш к CDN-ресурсам или (лучше для PWA) разместить `highlight.js` локально и кэшировать в service worker.

### 3.5. PWA неполноценна

- В `manifest.json` только **одна иконка** (`favicon.png`, `sizes: "any"`). Для установки на Android/desktop нужны иконки **192×192** и **512×512** (в т.ч. `maskable`).
- Нет `screenshots` и `shortcuts`.
- Описание в manifest устарело (27 → 50).

**Рекомендация:** добавить корректный набор иконок, `screenshots`, `shortcuts`; обновить описание.

## 4. Незначительные улучшения (Low priority)

- **CSS:** единый файл ~1350 строк — можно разбить на модули (base / layout / components / themes) или организовать через слои `@layer` для поддерживаемости.
- **Доступность (a11y):** проверить `aria`-атрибуты для интерактивных элементов (меню-гамбургер, кнопки квизов, табы), контрастность тем; вынести инлайн-стили из `index.html` (~155 строк в `<head>`) в общий CSS.
- **Производительность:** ленивая загрузка тяжёлых компонентов (квизы/REPL), дефер скриптов.
- **Тестирование:** добавить хотя бы smoke-тесты (проверка ссылок между уроками, соответствие данных в `lessons.json`/`config.js`).
